## ③ 生成ログの最新20件より前の記事を開けない

### 原因

- `GET /api/generation-logs` が `listGenerationLogs(20)` に固定され、ページ・続きの指定がなかった。画面にもページ送り・検索はなく、21件目以降を開く手段がなかった。
- 取得件数の決まり方は保存経路ごとに以下のとおりだった。いずれも最終的に20件へ切り詰めていた。
  - Supabase直結：`updated_at` 降順で80行を取得し、ジョブ20件に絞る。
  - gateway：`list_jobs` に limit 20 を渡し、内部で80行を取得して20件に絞る。
  - ローカル保存：`updatedAt` 降順で20件。
- 記事本体（`article_drafts`）と生成ログ（`article_inputs` のジョブ）は別に保存している。ログの「開く」はジョブIDから正本の記事本体を読む。
- **削除ではない。** アプリには生成ジョブ・記事本体を削除する処理も、保存期限もない。削除処理は、画像差替え時の画像行とWordPress投稿予約の解放だけである。11/13記録では `article_inputs` 29行・`article_drafts` 26行が保存されていた。現在の本番件数は未確認。
- 所有者・組織による絞り込みはない（共有アクセスコード方式で、全ログが同じ範囲）。今回の変更でも範囲は同じで、未認証アクセスは従来どおり401になる。
- 旧一覧は更新日時順だったため、保存・投稿のたびに記事の位置が動いていた。一方、表示している日時は作成日時だった。

### 対応

- API: `GET /api/generation-logs?cursor=...`（サーバー発行の不透明カーソル）と `?limit=`（1〜100）を追加した。応答は `{ logs, nextCursor, complete }` である。1ページ目のURLは従来と同じ。
- 並び順: **作成日時の新しい順＋ID** に変更した。作成日時は変わらないため、保存・投稿してもページ間で重複・欠落しない。
- 保存経路ごとの処理:
  - Supabase直結：SQLでキーセット取得（limit+1）。
  - gateway：既存の `list_jobs` を最大窓（100ジョブ／最新更新400行）で呼び、サーバー内でページングする。窓が満杯のときは `complete:false` を返し、画面に注意を表示する。**Edge Function の変更・再デプロイとDBマイグレーションは不要。**
  - ローカル保存：同じキーセット処理。
- 画面:
  - 生成ログの下に「さらに古いログを表示（20件ずつ）」を追加した。
  - 件数表示は「20件表示（続きあり）」とし、最後まで表示すると「最も古い生成ログまで表示しています。」と出す。
  - 続きの取得に失敗しても表示中の一覧は残り、再試行できる。
  - 投稿後などの自動更新では、表示済みの範囲（最大100件）を取り直す。
- 開いた記事は同じ記事IDのまま保存され、既存のWordPress投稿導線へ進める。記事数は増えない。
- 自動削除・保存期限は追加していない。

## ② ドラフト保存後に「処理中」が消えない

### 原因

- 生成完了時に、`runArticleGenerationJob` が次の2つを**別々に**保存していた。
  1. ジョブを `completed` にする
  2. 「ドラフト保存」ステップを `done` にする
- 画面は `completed` を見た時点で状況確認（ポーリング）を止める。そのため、1と2の間に確認すると「ドラフト保存：処理中」が表示されたまま固定される。記事本体は1より前に保存済みで、生成ログにも「完了」と記録される。顧客の報告「生成ログに記録されるが処理中のまま」と一致する。
- 再現: 書込み直後のポーリングを模擬する結合テストで、`completed` かつ save=`running` の応答を観測した（修正前 3 failed）。
- 構成による差: この処理に構成別の分岐はない。発生するかは確認のタイミング次第である。比較型・FAQ型で起きた点については「記事が大きいほど2回の書込みが遅く、すき間が長い」可能性があるが、**未検証の仮説**である。
- 2が失敗した場合や処理が途中で終了した場合は、DBにも save=`running` が残り、開き直しても「処理中」と表示され得る。
- 付随する問題も確認した。
  - 保存とポーリングにタイムアウトがなく、通信切断時には「失敗」と断定していた。
  - 時間切れ後に再保存すると、遅れて届いた古い保存が新しい保存を上書きする余地があった。

### 対応

- 完了状態と保存ステップ完了を**1回の書込み**に統合した。
- 過去に「完了・save=running」で記録されたジョブの扱い:
  - 正本の記事本体を読めた場合だけ、表示上「ドラフトを保存しました」とする。DBは書き換えない。
  - 読めない場合は「保存された記事本体を確認できませんでした…」と表示する。
- 保存・承認:
  - 60秒で打ち切る。応答なし・切断・ゲートウェイ応答（502〜504のHTML）は「保存できたかどうかを確認できませんでした」と表示し、失敗とは区別する。
  - 入力内容はそのまま保持する。再保存は同じ記事IDへの上書きなので、記事は増えない。
  - 二重クリックはrefで抑止する。
- サーバー: 保存・承認時、直前に読んだ正本リビジョンを条件に更新する（既存RPCの `expected_updated_at` を利用）。遅延した旧リクエストは409で拒否され、新しい保存を上書きしない。応答だけが失われた保存の再試行は成功する。
- ポーリング: 一時的な通信断は最大4回まで再試行する。続く場合は「状況を確認できませんでした」と表示して、処理中の表示を止める。ジョブIDは保持するので、再読み込みで確認を再開できる。
- 生成開始の結果が不明な場合は、重複生成を避けるため、生成ログで確認するよう案内する。

## 相沢様向け操作手順（案）

1. 画面の「生成ログ」の「開く」を押す。作成日時の新しい順に20件表示される。
2. 一覧の下の「さらに古いログを表示（20件ずつ）」を押すと、それより前の記事が20件ずつ追加される。最後まで表示すると「最も古い生成ログまで表示しています。」と表示される。
3. 「WordPress」列が「未投稿」の記事の「開く」を押す。本文、手編集の内容、記事構成、表・末尾FAQの設定、入力内容が復元される。
4. 編集して「編集内容を保存」を押し、「編集内容を保存しました。」と表示されることを確認する。編集・投稿しても、一覧での並び順は変わらない。
5. 「承認済みに変更」を押し、これまでと同じ手順でWordPressへ投稿する。
6. 「保存できたかどうかを確認できませんでした」と表示された場合も、入力内容は画面に残っている。少し待って「編集内容を保存」をもう一度押す。同じ記事に保存されるため、記事は増えない。
7. 記事作成の「生成状況」の「ドラフト保存」は、完了すると「ドラフトを保存しました」と表示される。

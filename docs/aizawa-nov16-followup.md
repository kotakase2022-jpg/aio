## ③ 生成ログの最新20件より前の記事を開けない

### 原因

- `GET /api/generation-logs` が `listGenerationLogs(20)` に固定され、ページ・続きの指定がなかった。画面にもページ送り・検索はなく、21件目以降を開く手段がなかった。
- 取得件数の決まり方は保存経路ごとに以下のとおりだった。いずれも最終的に20件へ切り詰めていた。
  - Supabase直結：`updated_at` 降順で80行を取得し、ジョブ20件に絞る。
  - gateway：`list_jobs` に limit 20 を渡し、内部で80行を取得して20件に絞る。
  - ローカル保存：`updatedAt` 降順で20件。
- 記事本体（`article_drafts`）と生成ログ（`article_inputs` のジョブ）は別に保存している。ログの「開く」はジョブIDから正本の記事本体を読む。
- **削除ではない。** アプリには生成ジョブ・記事本体を削除する処理も、保存期限もない。削除処理は、画像差替え時の画像行とWordPress投稿予約の解放だけである。11/13記録では `article_inputs` 29行・`article_drafts` 26行が保存されていた。現在の本番件数は未確認。
- 所有者・組織による絞り込みはない（共有アクセスコード方式で、全ログが同じ範囲）。今回の変更でも範囲は同じで、未認証アクセスは従来どおり401になる。
- 旧一覧は更新日時順だったため、保存・投稿のたびに記事の位置が動いていた。一方、表示している日時は作成日時だった。

### 対応

- API: `GET /api/generation-logs?cursor=...`（サーバー発行の不透明カーソル）と `?limit=`（1〜100）を追加した。応答は `{ logs, nextCursor, complete }` である。1ページ目のURLは従来と同じ。
- 並び順: **作成日時の新しい順＋ID** に変更した。作成日時は変わらないため、保存・投稿してもページ間で重複・欠落しない。
- 保存経路ごとの処理:
  - Supabase直結：SQLでキーセット取得（limit+1）。
  - gateway：既存の `list_jobs` を最大窓（100ジョブ／最新更新400行）で呼び、サーバー内でページングする。窓が満杯のときは `complete:false` を返し、画面に注意を表示する。**Edge Function の変更・再デプロイとDBマイグレーションは不要。**
  - ローカル保存：同じキーセット処理。
- 画面:
  - 生成ログの下に「さらに古いログを表示（20件ずつ）」を追加した。
  - 件数表示は「20件表示（続きあり）」とし、最後まで表示すると「最も古い生成ログまで表示しています。」と出す。
  - 続きの取得に失敗しても表示中の一覧は残り、再試行できる。
  - 投稿後などの自動更新と「更新」では、表示済みの範囲を取り直す。1回の取得は100件までで、それを超える範囲はカーソルで続けて取得してから一覧を置き換える。
- 開いた記事は同じ記事IDのまま保存され、既存のWordPress投稿導線へ進める。記事数は増えない。
- 自動削除・保存期限は追加していない。

## ② ドラフト保存後に「処理中」が消えない

### 原因

- 生成完了時に、`runArticleGenerationJob` が次の2つを**別々に**保存していた。
  1. ジョブを `completed` にする
  2. 「ドラフト保存」ステップを `done` にする
- 画面は `completed` を見た時点で状況確認（ポーリング）を止める。そのため、1と2の間に確認すると「ドラフト保存：処理中」が表示されたまま固定される。記事本体は1より前に保存済みで、生成ログにも「完了」と記録される。顧客の報告「生成ログに記録されるが処理中のまま」と一致する。
- 再現: 書込み直後のポーリングを模擬する結合テストで、`completed` かつ save=`running` の応答を観測した（修正前 3 failed）。
- 構成による差: この処理に構成別の分岐はない。発生するかは確認のタイミング次第である。比較型・FAQ型で起きた点については「記事が大きいほど2回の書込みが遅く、すき間が長い」可能性があるが、**未検証の仮説**である。
- 2が失敗した場合や処理が途中で終了した場合は、DBにも save=`running` が残り、開き直しても「処理中」と表示され得る。
- 付随する問題も確認した。
  - 保存とポーリングにタイムアウトがなく、通信切断時には「失敗」と断定していた。
  - 時間切れ後に再保存すると、遅れて届いた古い保存が新しい保存を上書きする余地があった。

### 対応

- 完了状態と保存ステップ完了を**1回の書込み**に統合した。
- 過去に「完了・save=running」で記録されたジョブの扱い:
  - 正本の記事本体を読めた場合だけ、表示上「ドラフトを保存しました」とする。DBは書き換えない。
  - 読めない場合は「保存された記事本体を確認できませんでした…」と表示する。
- 保存・承認:
  - 60秒で打ち切る。応答なし・切断・ゲートウェイ応答（502〜504のHTML）・成功応答の本文欠損は「保存できたかどうかを確認できませんでした」と表示し、失敗とは区別する。
  - 入力内容はそのまま保持する。再保存は同じ記事IDへの上書きなので、記事は増えない。
  - 二重クリックはrefで抑止する。
- サーバー: 保存・承認時、直前に読んだ正本リビジョンを条件に更新する（既存RPCの `expected_updated_at` を利用）。遅延した旧リクエストは409で拒否され、新しい保存を上書きしない。応答だけが失われた保存の再試行は成功する。
- ポーリング: 一時的な通信断は最大4回まで再試行する。続く場合は「状況を確認できませんでした」と表示して、処理中の表示を止める。ジョブIDは保持するので、再読み込みで確認を再開できる。
- 生成開始の結果が不明な場合は、重複生成を避けるため、生成ログで確認するよう案内する。
- WordPress投稿が切断・ゲートウェイ応答で途切れた場合は、重複投稿を防ぐため、WordPress管理画面で投稿の有無を確認してから再投稿するよう案内する。共通の通信処理を変えたことに伴う表示の調整で、投稿リクエストへのタイムアウトは追加していない。

## 遅れた書き込みによる記事の二重表示の防止（11/17、別PR kotakase2022-jpg/aio#54）

所有者が11/17に既知の制約として受け入れた次の2点を、別PRで解消する。**本番には未反映**（マイグレーション・gateway・アプリの反映はいずれも所有者の承認後）。

- 送信済みの保存要求・完了更新が、ブラウザがジョブIDを解放した後に Supabase で遅れて適用され、生成ログに記事が2件出る。
- ブラウザの時計が進むと、7分の保持が早く終わる。

### 対策

- DB: マイグレーション `20261117051104_guarded_generation_completion.sql` で、関数 `aio_complete_generation_job` を追加した。追加だけで、既存の関数・表・RLS は変更しない。1つのトランザクションで次を行う。
  1. ジョブの行をロックする（`for update`）。停止・失敗の書き込みとの順序が決まる。
  2. ジョブが「実行中」で、作成から6分未満であることを、DBの時計（`clock_timestamp()`）で確認する。満たさない場合は SQLSTATE `JOB01` で中止し、何も書き込まない。
  3. 読み込んだ後にジョブが更新されていないこと（`updated_at` の比較）を確認する。更新されていれば `40001` で中止し、アプリが読み直して再試行する。
  4. 既存の `aio_save_draft` で記事本体と画像を保存し、同じトランザクションでジョブを「完了」に更新する。既存の記事は上書きしない（同じIDの記事があれば中止）。
  5. 書き込みの後にもう一度期限を確認する。途中で遅れて期限を過ぎた場合は、全体を取り消す。
  - 実行権限は service_role だけ（`aio_save_draft` と同じ）。`security invoker`、`search_path` 固定。
- gateway（`aio-store`）: 操作 `complete_job` を追加した。`JOB01` は 409「Generation job can no longer be completed.」、`40001` は 409 で返す。既存の操作は変更していない。
- アプリ: 生成処理の最後にある「記事本体の保存」と「ジョブの完了」を、この1回の書き込みにまとめた（Supabase直結・gateway・ローカル保存の3経路）。DBが拒否した場合、ジョブは「記事生成が制限時間を超えたため停止しました」として失敗になり、記事は保存されない。編集画面の保存・承認（`aio_save_draft`）、画像の再作成、WordPress投稿は変更していない。
- ブラウザ: 状況を読めないまま再確認したときの「7分」の判定を、サーバーの時計で行う。開始時にサーバーが返したジョブの作成日時を保存し、失敗した応答の `Date` ヘッダー（サーバーの現在時刻）と比べる。ブラウザの時計が進んでも、保持は早く終わらない。どちらかが得られない場合だけ、従来どおりブラウザの時計で判定する。画面の表示・文言は変更していない。

これにより、ブラウザがジョブIDを解放する時点（サーバー時刻で作成から7分以降）では、DBはそのジョブの完了を受け付けない（作成から6分以降は拒否）。解放の後に、前回の記事が遅れて増えることはない。

      - ゲートウェイ経路だけの場合、`+00:00` なら `list_job_page` で取得している。
  - 確認できるまでは、ジョブが100件を超えると古いログが一覧に出ない可能性がある（画面に注意を表示する）。
- 本番での書き込み確認（既存の未投稿記事の保存確認、合成生成1件）は未完了。1回目は、入力したアクセスコードが受け付けられずログインで停止した（書き込みなし）。アクセスコードの件が片付くまで保留している。
- 所有者の判断（11/17）:
  - 遅れた書き込みによる重複の可能性（上記）は、既知の制約として受け入れる。→ 対策を別PRで実装した（上記「遅れた書き込みによる記事の二重表示の防止」）。本番に反映するまでは、この制約が残る。
  - ログインコードの既定値の削除は、本番の `DEMO_ACCESS_CODE` を確認・設定した後に、別作業で行う。
- 保存・投稿時の生成ログ同期（題名・投稿状態の更新）は、既存仕様のまま最新更新の100ジョブを探索している。100件を超えた状態で古い記事を保存すると、一覧の題名・投稿状態が更新されない可能性がある。記事本体の保存には影響しない。
- WordPress投稿リクエストにはタイムアウトを追加していない。既存の投稿予約による重複防止に委ねている。
- 保存直前リビジョンによる比較は、サーバーで読み取った後の遅延（DB・gatewayでの遅延）を防ぐ。次の2つは防げず、CodeRabbitも指摘している。今回は見送り、理由をPRに記録した。
  - サーバーで読み取る**前**に遅れた旧リクエスト。60秒の時間切れ後の再試行に限らない。通信断の直後にすぐ再試行し、旧リクエストの処理開始が再試行の保存完了より遅れた場合にも起こり得る。当初「60秒以上遅れる場合に限られる」と記載したのは不正確だったため訂正した（CodeRabbitの指摘による）。
  - 複数の画面・利用者が同じ記事を同時に編集した場合は、従来どおり後から保存した内容が残る。今回の変更前からの挙動で、今回の比較更新では防げない。
  - 未保存の下書きへの同時の初回保存。通常の流れでは、記事本体は生成時にサーバーで作成済みであり、正本を持たない旧ログの記事に限られる。
  根本対策には、クライアント側で基準リビジョンを管理し、要求IDで再送を識別する仕組みと、「行が存在しないこと」を条件にした作成が必要になる。後者はRPCの変更（マイグレーション）を伴う。
- 生成完了前に処理が途中で終了したジョブの記事本体が、ログに紐づかない可能性（既存の事象で、今回は未対応）。

■ ③ 生成ログの最新20件より前の記事を開けない件
原因：生成ログの一覧が最新20件だけを読み込む作りになっており、それより前の記事を画面から開く手段がありませんでした。記事のデータは削除されておらず、保存されたままです。
対応：生成ログの一覧の下に「さらに古いログを表示（20件ずつ）」を追加しました。過去の記事も開いて、編集・保存・WordPress投稿まで、これまでと同じ手順で行えます。一覧は作成日時の新しい順に並び、編集や投稿をしても並び順は変わりません。

■ ② ドラフト保存後に「処理中」が消えないことがある件
原因：記事作成の完了時に、「完了」の記録と「ドラフト保存」欄の完了の記録を別々に行っていました。その間に画面が状況を確認すると、記事は保存済みにもかかわらず「処理中」のまま止まることがありました。記事構成の種類ではなく、確認のタイミングによって起こるものでした。
対応：完了の記録を1回にまとめ、保存が終わると「ドラフトを保存しました」と表示されるようにしました。以前「処理中」のまま記録された記事も、記事本体が保存されていれば、開き直すと保存済みとして表示されます。また、通信が途切れた場合や応答がない場合も「処理中」のまま止まらず、保存できたかを確認できない旨と、もう一度操作する方法を表示します。通信が不安定なときに、同じ記事作成が二重に始まらないような確認も加えました。
